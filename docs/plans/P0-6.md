# P0-6: server base

**Goal:** the Worker runs locally with the kill switch, CORS, per-IP limits, household signatures, the KV spending cap, `/topup` and `/register`; deployment remains the owner's step.

**Research read:** hosting.md (Workers limits), ens-v2.md §3, viem.md; ADRs 0002, 0003 and 0006. Existing plan followed and updated 2026-11-06.

**Agreed seams:** guard/chargeSpend with fake KV and a fixed signing key; relay operations with fake JSON-RPC; signed client HTTP requests. These verify authentication, limits and transaction intent without broadcasting or reading real secrets.

**Files:** `server/src/index.ts`, `guard.ts`, `http.ts`, `chain/relay.ts`, `routes/topup.ts`, `routes/register.ts`; `src/lib/server-client/signed.ts` (new) and the `topup`/`registerName` bodies in `src/lib/server-client/index.ts`; `scripts/fund-relay.mjs`.

**Tests first** (`server/src/guard.test.ts`, `server/src/chain/relay.test.ts`):

- kill switch on → 503 for routes, `/health` still answers;
- a disallowed `Origin` → 403; no `Origin` (curl, scripts) is allowed;
- missing or malformed signature headers → 401; a wrong signer, a changed body, or a timestamp more than 120 s away → 401;
- a valid signature passes and the route sees the signer's address and the exact body bytes;
- the 31st request from one IP in a minute → 429;
- the spend counter refuses once today's total would pass `DAILY_SPEND_CAP_CENTS`;
- top-up amount: nothing at or above half the target, otherwise send the fixed target amount;
- register refuses a label that breaks ADR 0006's rule, a taken label, and contracts not deployed through the VerifiableFactory from the expected implementations.

**Decisions:**

- Signatures: EIP-191 over `signedMessage(route, timestamp, sha256(body))` (shared/api.ts), checked with viem `verifyMessage`. A replay inside the 120 s window is possible; the per-IP limit, the per-household top-up limit and the spend cap bound it.
- `/register` checks with `VerifiableFactory.verifyContract` that the resolver is a PermissionedResolver proxy and the grant registry a UserRegistry proxy, so nobody points a household name at arbitrary code. One name per household address.
- Provisional top-up targets (constants in `chain/relay.ts`): Sepolia 0.002 ETH, Rabdi 0.2 tGLM. The P0-3 hour-0 gas row is still empty: these are not measured gas budgets and must be revisited after that test. Below half the target, send the fixed target amount; at most one top-up per household per chain per 10 minutes. The relay waits for a successful receipt so the app can send its next transaction at once.
- Rabdi is defined with viem's `defineChain` on the server, so the Worker doesn't need the Arkiv SDK.
- KV free tier allows 1,000 writes a day. Each request writes once for the IP counter; model routes add one for the spend counter. Enough for the event; noted as a limit.
- Errors: every route returns a plain message; viem errors and bodies never reach a response or a log.

**Risks:** Workers Free gives 10 ms CPU per request; `verifyMessage` and signing a transaction are the heaviest steps (measure after deploy). The relay needs Sepolia ETH as well as tGLM: `scripts/fund-relay.mjs` moves ETH from the deployer.

KV is eventually consistent and permits one write per key per second: counters, cooldowns and one-name checks are best-effort across isolates, not atomic global guarantees. Serialize mutations within an isolate and pace repeated counter writes. A strict global limit requires a Durable Object (outside this ticket). Do not run funding scripts or read `.env.local`. Use existing `server/.dev.vars` for local startup without displaying its values; if absent, create ignored dummy local bindings only, with no funded account or live relay test. Address/speech bodies remain owned by AI/ML and use the exported signing helper when implemented.
