# Page-to-page transitions

Checked: 2026-11-07 · Status: answered; device verification required
Scope: between-route motion only; the approved home intro remains separate. Research only: no dependencies, app code, commits or deployments.

## Decision

**Pata-specific recommendation:** use a short arrival effect on the existing content region: opacity about 0.94 → 1 and translateY 6px → 0 over about 200ms, ease-out. Keep the header outside that region, stationary; retain the cream surface, forest-green type and existing gold accents. Add no screen-covering panel, badge, progress line, text or loader. This is an arrival animation after navigation commits, not a captured old/new-page crossfade.

Use a persistent, **unkeyed** client wrapper in the shared layout. Observe `usePathname`; after the first render, animate the existing wrapper DOM element when pathname changes. Do not key the wrapper by pathname, introduce a template solely to replay motion, duplicate the previous page, delay links, intercept clicks/history, or retain sensitive page trees for exit animation. React keys deliberately reset subtree state; an unkeyed wrapper avoids adding another reset beyond ordinary routing. `usePathname` reads the pathname and re-renders on route changes without fetching that client component again. [React state identity](https://react.dev/learn/preserving-and-resetting-state), [Next usePathname](https://nextjs.org/docs/app/api-reference/functions/use-pathname).

Prefer the browser Web Animations API for this bounded effect, with feature detection and immediate visible fallback. Keep base CSS fully visible and interactive; animation completion must never unlock content. Store/cancel the previous animation before starting another and on cleanup. A rejected `finished` promise after cancellation must be handled if used. Do not clear styles from a stale completion callback after a newer animation starts. These are implementation recommendations based on the [Web Animations cancellation model](https://drafts.csswg.org/web-animations-1/#canceling-an-animation-section).

Under reduced motion, skip the effect entirely; observe preference changes and cancel an active effect immediately. Do not require hover, drag, pointer tracking, scroll gestures or new controls. A small content translation uses the same behavior on touch and laptop without a viewport-sized sweep. The preference is defined by the [Media Queries specification](https://drafts.csswg.org/mediaqueries-5/#prefers-reduced-motion).

## What the requested libraries actually supply

The corrected first-party Watermelon origin is `ui.watermelon.sh`, as established in the [previous intro note](frontend-intro-components.md) and its [developer index](https://ui.watermelon.sh/llms.txt). The following public source was read directly on this date; no private or Pro source was fetched.

- **Watermelon ScrollFade:** [source](https://raw.githubusercontent.com/WatermelonCorp/watermellon-registry/main/src/components/watermelon-ui/scroll-fade.tsx) is a scroll container with conditional edge gradients, scroll listeners and `ResizeObserver`; imports React and local `cn`. This is an overflow affordance, not route fading. Its decorative overlays correctly use `aria-hidden` and `pointer-events-none`; borrow that principle only if decoration is needed. It adds nested overflow and optional scrollbar hiding that Pata's page wrapper does not need.
- **Watermelon Revealing Cards:** [source](https://raw.githubusercontent.com/WatermelonCorp/watermellon-registry/main/src/components/watermelon-ui/revealing-cards.tsx) implements a fixed 300px card stack with `framer-motion`, drag thresholds, rotation and scale. No reduced-motion branch or route integration appears. Reject for page transitions: swipe gestures and fixed-width cards solve a different problem. The [registry manifest](https://raw.githubusercontent.com/WatermelonCorp/watermellon-registry/main/registry.json) lists `framer-motion`, `motion`, `react`, while this actual file imports `framer-motion` and React. No item name containing `transition` was found in that manifest; this bounded inspection does not prove the entire catalog lacks a route example.
- **Skiper free Theme toggle / skiper26:** [component docs](https://skiper-ui.com/v1/skiper26), [complete public source](https://skiper-ui.com/r/skiper26.json). This is the closest technical reference: `document.startViewTransition` with an unsupported-browser fallback, CSS pseudo-elements and rectangle/circle reveals. Actual imports include `framer-motion`, `next-themes`, `lucide-react`, React and local `cn`; metadata only declares `framer-motion`. It injects global root-transition styles, with rectangle reveals around 0.7s and other variants up to 3s, plus optional blur/GIFs. No reduced-motion guard appears. It changes theme, not routes, and offers no router-commit coordination. A click works on touch, but the draggable demo options are irrelevant. Borrow the idea of one restrained transition, not its code, theme provider or global root sweep.
- **Skiper Nike / Pixel preloaders:** public [Nike docs](https://www.skiper-ui.com/v1/skiper7) and [Pixel docs](https://www.skiper-ui.com/v1/skiper11) label both Pro and show timed preloaders using `AnimatePresence`; they are not evidence of an available free route-transition implementation. Do not install them or fetch protected source. They would also repeat the existing intro's role.

Watermelon's [MIT license](https://raw.githubusercontent.com/WatermelonCorp/watermellon-registry/main/LICENSE) requires retaining its notice for copied substantial source. Skiper26's source notice and docs require Skiper UI attribution for free-source use; Pro removes that requirement. Do not call Skiper MIT. This recommendation writes original small browser/React glue rather than adapting either component, so neither library needs to be installed or copied.

## Native View Transition API and Next static export

- Native same-document transitions require capturing before and after the actual DOM change; simply wrapping `router.push()` does not establish that the asynchronous Next route commit occurred inside the snapshot callback. Triggering one from a pathname effect is too late to capture the departing route. The browser API creates snapshot pseudo-elements over the page; only one transition runs at once and a new one ends the previous animation. [Chrome same-document guide](https://developer.chrome.com/docs/web-platform/view-transitions/same-document).
- Current [React ViewTransition docs](https://react.dev/reference/react/ViewTransition) coordinate DOM commits, and explicitly advise against independently calling `startViewTransition` when React owns transitions. React can interrupt independent transitions; React-managed rapid updates are batched. Reduced motion is **not** automatic. The public page currently documents React 19.3: verify the installed React and version-matched Next 16.4 docs before enabling this integration. This note does not establish that Pata's installed runtime exports that component or that a Next experimental flag is production-safe.
- Cross-document CSS `@view-transition { navigation: auto; }` requires same-origin document navigations and opt-in on both documents. It can decorate exported HTML full loads in supporting browsers, but it does not turn Next client-side links into cross-document navigations. Do not switch normal links to full reloads merely to obtain motion. [Chrome cross-document guide](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document).
- The recommended client effect uses exported HTML plus browser hydration; it needs no route handlers, server actions, middleware or runtime server. Keep browser API access inside client effects. Local `node_modules/next/dist/docs/` is authoritative for the installed version; the implementing session must confirm the layout/client-wrapper behavior and run the static export build. Use existing namespaced global CSS if styling is needed; the intro note records the project's CSS Module export-map issue.

## Navigation, sensitive state and verification

Do not read or include `location.hash`, courier session keys, query strings or page data in animation identifiers. Observe only pathname: same-path fragment changes and query updates do not replay this decoration. Preserve ordinary Next links, modified clicks, external navigation, focus, scroll restoration, deep-link parsing and Back/Forward behavior. Skip initial-load motion so direct `/c#...`, `/approve`, `/setup`, `/lookup` and home intro startup remain immediate. Keep courier expiry/error transitions in the live page; never retain a screenshot or a duplicated previous courier view merely to crossfade it.

Rapid navigation should cancel the old decoration and show the latest committed content immediately. Route focus and scrolling must remain the router's responsibility; do not focus a wrapper as an animation side effect. A transform can change the containing block for fixed descendants, so inspect the actual content subtree before animating its ancestor; if a fixed overlay/map control depends on viewport positioning, prefer opacity-only or animate a smaller safe region.

Verify: phone portrait/landscape and laptop; reduced motion before load and changed during motion; repeated fast route changes and Back/Forward; unmodified/modified link clicks; direct courier fragment intact; query/hash-only changes; setup form/map/passkey state unaffected by wrapper rerenders; courier expiration remains immediate; existing intro plays once through its own lifecycle; animation API absent/failing still shows content; static export succeeds. No performance or compatibility claims are considered device-tested by this note.
